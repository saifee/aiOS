# Security audit: October 2026 (v1.6.0)

Scope: the whole application (API, web app, public booking pages, webhooks, static file serving, dependencies, deployment files).
Method: reading every route, an automated check that every route file is behind the sign-in hook, live attack probes against a running build, dependency audit, and the automated test suite (80+ tests).

## Result in one line
No data exposure, no unauthenticated access to private data, no known vulnerable dependencies. Four hardening gaps were found and fixed; bot protection and brute-force defence were added.

## Questions answered
| Question | Answer |
|---|---|
| Is anything exposed? | No. `/.env`, `/.git`, `/package.json`, `server.js`, `schema.sql`, `node_modules`, source maps, dotfiles and `..` path tricks (plain, URL-encoded, double-encoded, NUL byte) all return 404. `npm audit` reports 0 vulnerabilities. No secrets are tracked in git (the two template env files contain placeholders only). |
| Can anyone "play" via links? | Private links are random and unguessable: booking cancel/download links (144-bit token), calendar subscription feed (192-bit token). Public booking pages expose only the title, meeting types and open hours; never emails, attendee names or settings. Every private API route (59 of them) returns 401 without a valid token and checks tenant membership on every ID (`requireBusiness`). |
| Is the directory hidden? | Yes. No directory listing exists. Only the built web files are served, and only for real pages. Unknown paths now get a proper 404 page (before: the home page with status 200). Non-GET methods on pages return 405 (before: 200). |
| Are all areas secured? | Yes, see the checklist below. |
| Captcha? | Added: Cloudflare Turnstile or Google reCAPTCHA v2, your choice via three environment variables. |

## Fixed in this release
1. **No bot check or lockout on sign-in.** Added captcha (sign-in, sign-up, first-run setup, public booking) and an escalating lockout: 5 wrong passwords per email+IP, 25 per email from anywhere, 40 per IP across emails, each locking for 15 minutes with a `Retry-After` header. The email+IP pairing means a stranger cannot lock you out of your own account.
2. **Weak passwords accepted.** Passwords must now be 10+ characters and not common, repetitive, or contain the person's email name or first name.
3. **HTML injection in booking emails.** A guest could put markup in their name or notes and it would render in the owner's notification email. All guest-supplied fields are now escaped.
4. **`javascript:` links.** Booking meeting links and the company booking link accepted any URL scheme; only http(s) is accepted now.
5. **Static server too permissive.** Unknown paths returned the home page with 200, and TRACE/PUT/DELETE were accepted on pages. Now 404 / 405.
6. **CSP** opens exactly the captcha provider in use and nothing else.

## Verified OK (no change needed)
- Passwords: argon2/scrypt hashing, constant-time verify against a dummy hash when the account does not exist.
- JWT: HS256 only, algorithm pinned, live membership check (removed users lose access within 60 s), secret enforced at startup.
- Tenant isolation: every `:id` route loads the record, then verifies the caller belongs to its business; covered by tests.
- Mass assignment: request schemas are strict; unknown fields are rejected.
- SQL injection: Prisma parameterised queries only; JSON-operator payloads (`{"$ne":null}`) are rejected by validation.
- Webhooks (WhatsApp, Twilio, SendGrid, Cal.com, Stripe): signature verified; unsigned requests rejected in production.
- SSRF: custom AI endpoints go through a private-address guard.
- Secrets at rest: AI keys, WhatsApp tokens and Stripe secrets are AES-256-GCM encrypted; never returned by the API.
- Headers: HSTS, CSP, X-Frame-Options DENY, nosniff, strict referrer policy, COOP/CORP; `Cache-Control: no-store` on all API responses; pages are `no-cache`.
- CORS: only APP_URL (+ CORS_ORIGINS); a foreign origin gets no CORS headers.
- Rate limits: 300/min global, 10/min on sign-in and sign-up, 10/min on public booking, 5/min on "email me now".
- Sign in with Google/Microsoft: signed one-time state + cookie binding, nonce, audience/issuer/expiry checks, and no account linking on unverified emails.

## Residual risks (accepted or for you to decide)
| Risk | Why | What to do |
|---|---|---|
| Tokens live in browser storage | Standard for single-page apps; an XSS bug would expose them. The CSP allows inline scripts because the Next.js static export needs them. | Keep dependencies updated; no user HTML is rendered anywhere (all React-escaped). Moving to HttpOnly cookies is a larger change. |
| No instant sign-out everywhere | Tokens last 24 h (`JWT_EXPIRES_IN`). Removing a user from a workspace takes effect within 60 s; changing a password does not revoke existing tokens. | Lower `JWT_EXPIRES_IN` (e.g. 8h) if you want. |
| Sign-up reveals whether an email is registered | Needed for a clear message. Rate limit + captcha make mass harvesting impractical. | Accept, or switch to a generic message later. |
| Lockout state is in memory | Resets when the app restarts. | Captcha and the per-IP rate limit still apply. |
| Unsubscribe links (`/u/<id>`) have no page yet | Not a security issue, but outreach emails link to it and it returns 404. | Tell me and I will build the unsubscribe page. |
| 2-factor authentication | Not available yet. | Recommended next step for admin accounts; Google/Microsoft sign-in gives you their 2FA in the meantime. |

## Your actions
1. Set `CAPTCHA_PROVIDER`, `CAPTCHA_SITE_KEY`, `CAPTCHA_SECRET` (see `.env.example`).
2. Put the site behind Cloudflare (free plan is enough) with `TRUST_PROXY=true`: it adds DDoS absorption and a web firewall in front of the app.
3. Set `SETUP_TOKEN` (or complete setup and leave it, since setup disables itself after the first account), `SUPERADMIN_EMAILS`, and a strong `JWT_SECRET` / `ENCRYPTION_KEY`.
4. Rotate any secret that was ever pasted into chat or committed (including the old `.env.hostinger`).
